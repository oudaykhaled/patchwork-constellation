# Grouping revisions and local durability

Set `GROUPING_STORAGE_PATH=.data/grouping-history.json` for durable overrides on one host. The application remains explicit about `local-file` versus `process-memory` in capabilities. This file contains file IDs, paths, group names, model explanations and revision metadata. It contains no provider keys or source excerpts. Store it outside served assets, restrict OS access, back it up as application data, and do not commit it. `.data/` is ignored.

Each accepted mutation has a unique revision, pinned canonical hierarchy, provenance, locks and a delta containing previous memberships/names. Undo produces a new accepted revision with `restoresRevisionId`, returns the restored membership/group structure and reduces a finite undo stack. `canUndo` is authoritative; a non-null parent alone does not imply another undo exists. Accepted model explanations and model versions survive reload. Manual operations remove explanations invalidated by their overrides.

History writes use a same-directory temporary file, `fsync`, atomic rename, an exclusive lock and generation compare-and-swap. A second process reloads the latest generation before reading or editing. HTTP mutation preconditions are mandatory: `expectedRevisionId` on apply/mutate/undo/reject. A stale revision returns HTTP 409 `REVISION_CONFLICT`, preserving the winning state. The store bounds 100 contexts, 20 undo revisions per context and a 20 MB serialized file. This is single-host durability, not a shared multi-host database or a distributed transaction with snapshot storage. A shared transactional adapter is required before horizontal deployment.

`ownerGroupingStoragePath(base,ownerId)` produces separate hashed filenames for authenticated owners. Every grouping method must also receive the same tenant ID, including `view`, current/diff/reject, worker recovery and purge. A valid snapshot ID is not authorization; server routes must authorize the current repository before obtaining a grouping result.

When inventory refreshes, manual overrides migrate only over a surviving stable context identity or explicit rename evidence (`lineageAliases` / observed renamed-file comparison). An added/source-only identity is not proof of continuity. Ambiguous delete/recreate, conflicting aliases and removed/deleted files create `revision.reviewItems`; their proposed baseline membership stays usable. Unlocked files use the new deterministic hierarchy. Pure source-overlay inventory changes preserve the grouping revision ID and island IDs, while their old proposals fail an inventory compatibility check. Actual physical inventory/context changes receive a new revision.

`purgeRepository(repository,tenantId)` removes matching durable histories and proposals, invalidates cache entries and aborts/fences in-flight grouping so a late provider cannot recreate a revoked result. A changed disk generation prevents a stale process from committing its old state. The server must first revoke current authority and retain an authorization barrier; a local history file cannot independently determine whether a new caller is allowed to create new work.

Recovery: on `STORAGE_BUSY`, wait for the current writer and reload. If a process was killed while holding `.lock`, stop every process using that history path, verify the owner process has exited, back up the history, then remove only that lock and restart. Never automatically break a live lock. On invalid data or disk failure, edits fail closed with HTTP 503 rather than silently switching to memory. Restore a verified backup. Version-1 files from the earlier prototype lack the versioned canonical/provenance contract; preserve them as backups and review/reapply overrides through a known snapshot rather than inventing missing ancestry or silently trusting them.

API surface: `GET /api/grouping/current?snapshotId=…` returns `{snapshot,revision,canUndo}`. `POST /api/grouping/diff` with `{snapshotId,proposalId?}` returns a versioned delta without applying. `POST /api/grouping/reject` requires `{snapshotId,proposalId,expectedRevisionId}`. Apply/mutate/undo return `{snapshot,revision,canUndo,delta}`. Source counts, paths, import edges and pinned context are preserved by these operations.
