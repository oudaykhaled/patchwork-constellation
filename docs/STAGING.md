# Disposable staging deployment

The selected nonproduction host is an **ephemeral GitHub Actions Ubuntu 24.04 runner**, with Node 24, the pinned pnpm version and the runner's actual installed native PostgreSQL. This is a real application/artifact/database deployment inside one isolated job, with a stable loopback HTTP traffic proxy. It is not a public hosted beta or a persistent cloud service. The runner is destroyed after the job. The [official runner inventory](https://github.com/actions/runner-images/blob/main/images/ubuntu/Ubuntu2404-Readme.md) is the software source; the actual database version and machine/runtime conditions are recorded in each report.

Dispatch [Release candidate](../.github/workflows/release.yml) with `stage=staging`, the full reviewed candidate `commit` and a **distinct compatible reviewed ancestor** `rollback_commit`. The rollback source must include `DATABASE_AUTO_MIGRATE=false` support. A source preceding that configuration is not a qualified DML-only deployment. The workflow never substitutes the candidate as its own rollback artifact.

```sh
gh workflow run release.yml --repo oudaykhaled/patchwork-constellation \
  --ref <branch-containing-the-reviewed-workflow> \
  -f stage=staging -f commit=<full-reviewed-candidate-sha> \
  -f rollback_commit=<full-compatible-reviewed-prior-sha>
```

The workflow installs both exact committed sources with their frozen lockfiles and registry access, builds them and creates verified versioned archives with manifests and checksums. This preparation warms both package blobs and pnpm's supply-chain policy metadata; a package cache by itself is insufficient. Policies stay enabled and neither lockfile is rewritten. The later extracted-artifact deployment remains strictly offline. It starts a new SCRAM PostgreSQL cluster bound only to `127.0.0.1:55438`, using the runner's installed native server and matching backup/restore tools. Unix sockets are explicitly disabled so a distribution's root-owned socket directory cannot prevent unprivileged startup. No pre-existing cluster is edited. Real PostgreSQL storage, durable webhook and hard-killed-coordinator recovery tests run before the deployed BFF isolation/resource report from issue #28. Extracted installs explicitly retain development dependencies because the declared server runtime includes the pinned `tsx` package.

The release rehearsal then:

1. Creates two uniquely named disposable databases and a separate non-superuser serving role. A migration principal installs migrations 001/002; the serving role receives schema usage and table DML only. An actual `CREATE TABLE` attempt by that role must be denied.
2. Writes one synthetic persistent snapshot/job and records their canonical digests. Both archives are checksum/manifests verified, safely extracted and installed offline with their frozen lockfiles.
3. Starts the prior artifact, then the candidate, as ordinary production Node processes using the serving role and `DATABASE_AUTO_MIGRATE=false`. Every process receives disabled/cleared App and model configuration. A loopback proxy switches its active upstream while keeping one client address.
4. Verifies actual worker/storage/queue readiness, exact built HTML bytes, HTTP retrieval of the persistent snapshot, the 212-file demo and observed zero provider requests at every traffic phase.
5. Takes a native custom PostgreSQL backup, restores into the second **fresh** database, compares the snapshot/job digests and reapplies the compatible migrations with the migration principal. Starts the distinct prior artifact against the restored database and switches traffic back to it.
6. Stops its owned proxy/application processes, drops only its two generated databases and serving role, and stops its owned PostgreSQL cluster. It uploads only allowlisted redacted JSON and source/build artifacts for 14 days. Backups, cluster files, passwords, arbitrary logs and installed dependencies are excluded.

| Authority | Owner and lifetime | Access |
| --- | --- | --- |
| Workflow invocation | Repository maintainer through GitHub | Dispatch only; production acceptance remains separate |
| Actions token | GitHub, per job | `contents: read`; no deployment, repository write or provider secret references |
| Disposable database administrator | Generated inside the runner, per job | Cluster initialization, migrations and fresh database restore; masked connection passed only through job environment |
| Serving database role | Generated by the rehearsal, per run | Required table DML only; no superuser, database creation, role creation or schema CREATE |
| GitHub App and model accounts | Their actual maintainer | Not configured or used by this staging job |

The staging environment name records the target. Environment protection/reviewer settings must be read back separately; a YAML `environment` field does not establish approval controls. Production continues to require the exact reviewed same-commit acceptance record. This workflow neither creates that record nor tags/publishes a release. Human accessibility, live account/model evaluation, independent holdout review and intelligence rollout approval remain separate original gates.

For a local reproduction with the protected disposable PostgreSQL helper, set `STAGING_REHEARSAL=1`, `STAGING_CANDIDATE_ARCHIVE` and `STAGING_PREVIOUS_ARCHIVE` to committed archives, then run the opt-in `tests/release/staging.test.ts`. The helper supplies credentials without printing them. Direct runner command: `pnpm exec tsx tools/release/staging-rehearsal.ts <candidate.tar.gz> <previous.tar.gz> .tmp/staging/release-31.json`. Local reports say `local-disposable-staging`; only a completed Actions run may say `github-actions-ephemeral-staging`.
