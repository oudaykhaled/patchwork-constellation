## Remaining-issue follow-up

The original verification asks for staging resource/isolation scenarios and a correctness/coverage report. It does not explicitly require a production cloud service, real private-account fixtures, or a kernel sandbox. The staging gate therefore exercises the actual service/database boundaries using two authored accounts and a finite synthetic graph; it records those conditions without claiming external account or sandbox certification.

The first actual session/PostgreSQL run reproduced a real disconnect defect: another session for the same owner could still retrieve its private cached graph (`200` instead of `401`). Disconnect also left retained snapshots in storage. The corrected route inventories persisted snapshot/job/delivery and grouping repositories, revokes every owner session, and uses the existing cancellation/write fence before purging each scope. Discovery/token responses finishing after disconnect cannot restore authority. Another owner's equal snapshot ID remains usable. A previously retained repository absent from the current authorization binding registry is also removed.

`tests/backend-release/staging.ts` now verifies seven stages:

1. Real HTTP session issuance, CSRF denial, cross-owner and wrong-repository object isolation.
2. Live authorization discovery on cached token/snapshot reads; controlled removal returns `403` while the other account continues.
3. All 10,000 nodes and 40,000 edges from PostgreSQL-backed BFF routes, exactly 20/40 pages, no duplicates/dangling endpoints, each response below 512,000 bytes.
4. Request body `413` above 128,000 bytes and rejection of more than 20 selected sources.
5. Account-wide disconnect, cancellation/fenced storage/cache purge, retained-repository deletion, preserved second owner, and reconnect without resurrection.
6. Real signature verification, replay deduplication, durable inbox processing and cached/stored purge after an authored installation-removal webhook.
7. A separate actual HTTP service returns `429`/`Retry-After` after its configured four-request window.

The local gate passed on the recorded Windows/Intel host with PostgreSQL 17.11 and concurrent agents. The safe report includes elapsed phases, complete counts, actual payload maxima, process RSS observations and source revision/dirty state. RSS is diagnostic, not a memory-leak or capacity certificate. No source, connection URL, key, cookie, CSRF value or upstream token is written to the report. The final integrator must retain the hosted staging result for its exact integrated commit rather than presenting this preparation run as a hosted result.
